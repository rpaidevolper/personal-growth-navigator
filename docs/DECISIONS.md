# 決策紀錄（DECISIONS）

格式：`D-編號｜日期｜狀態`，接著「背景 → 決定 → 影響 / 替代方案」。新決策**往下追加**，不要改舊的；要推翻就新增一筆並註明取代哪一筆。
狀態：✅ 生效、♻️ 已被取代、⏳ 暫定

---

### D-001｜2026-10-22｜✅ 維持單一 HTML、無後端
背景：原工具就是單檔，擁有者希望個人先用、之後再擴展。
決定：所有功能寫在一個 HTML，資料存 localStorage，AI 由瀏覽器直連。
影響：不能做多人、不能做共編；擴展給他人靠「分享檔案 + 各自填 key」。

### D-002｜2026-10-22｜✅ AI 接法：Claude API 直連，使用者自備 key
替代方案：靜態資料不接 AI（無法客製）、自建後端（成本高）。
影響：需 `anthropic-dangerous-direct-browser-access` header；key 只存瀏覽器、匯出時清空。

### D-003｜2026-10-22｜✅ 模擬引擎：規則決定結果，AI 只做判斷與敘事
背景：全由 AI 推演會不穩定、難比較、每步花 token。
決定：規則引擎算狀態與分支；Claude / Jev 只回「成功機率」並與規則各半混合；Claude 另寫敘事。無 key 退回純規則。

### D-004｜2026-10-22｜✅ Jev（TypeSafe System One）列為選配判斷提供者
背景：擁有者提到 Jev；它是封閉式判斷模型（state + 問題 → 機率）。
決定：實作 `noul` 題型呼叫；因 early access 且瀏覽器 CORS 未驗證，**視為預留**，介面上說明清楚。

### D-005｜2026-10-22｜✅ 模擬參數：一步一季、一局 20 季、4 個狀態值、有受狀態影響的隨機事件
狀態值：專業深度 / 商業影響力 / 能見度 / 精力餘裕；不再加軸（避免資訊過載）。

### D-006｜2026-10-22｜✅ 本輪範圍只做模擬器 MVP，現況 / 目標 / 差距升級下一輪
理由：一次做完風險高；分階段、每輪可驗證。

### D-007｜2026-10-23｜✅ 介面收成 5 階段（總覽 / 現況 / 目標與差距 / 成長計畫 / 職涯模擬）
背景：原 7+1 分頁對新用戶資訊過載。
決定：導覽列即進度條；③④ 在 ①② 完成前鎖定；每頁一個「下一步」。

### D-008｜2026-10-23｜✅ 新用戶空白起始 + 「載入範例」
擁有者本人的資料改為範例資料；舊版 localStorage / 匯入檔自動升級並視為已完成設定。

### D-009｜2026-10-23｜✅ 能力自評採「一次一項、附 5 級描述」卡片；證照與經歷逐筆選單
取代整頁表格；表格保留在 ② 作微調用。

### D-010｜2026-10-23｜✅ 能力框架改為 Persona 對應的 10 項（4 核心 + 6 職類）＋ AI 客製 ＋ AI 追問（grill）
背景：原 14 項寫死給自動化顧問，非技術人員沒東西填；擁有者希望依基本資料生成、上限約 10 項、不足靠追問補。
決定：預建 5 職類框架為底，有 key 時 AI 微調並在自評後追問；離線仍可用。現有 14 項保留為擁有者專用框架。
替代方案（未採）：全由 AI 生成（必須有 key、難比較）；只預建不接 AI。

### D-011｜2026-10-23｜✅ Role model 做成精選原型庫 + AI 自訂，附免責
背景：擁有者希望用知名經理人增加趣味與理解。
決定：15–20 位，特質 → 能力權重；標示「依公開報導整理，非本人背書」；有 key 可自訂人物。

### D-012｜2026-10-23｜✅ 社群共編先做「資料外部化 + GitHub PR」，共編平台列 Phase 3
背景：維基式共編需要後端與審核，與 D-001 衝突。
決定：框架、角色、機會、role model 抽成 `data/*.json`，每筆帶來源與貢獻者；可匯入匯出；用 PR 貢獻。
待決：HTML 如何載入 JSON（`file://` 不能 fetch）——**已由 D-022 決定**（JSON 為來源、建置注入單檔 HTML、加執行期匯入框架包）。

### D-013｜2026-10-23｜✅ 機會改為規則生成並附理由
背景：目前 16 個機會為手寫，無通用依據。
決定：5 種通用型態 × 差距前 3 能力 × 門檻檢查；每張卡寫出理由；AI 可具體化。

### D-014｜2026-10-23｜✅ 計畫項目加入後要有「起步清單、本週視圖、季度回顧」
背景：使用者加入計畫後不知道具體要做什麼。

### D-015｜2026-10-23｜✅ 下一輪開發順序：2a（Persona + 框架 + grill）→ 2b → 2c → 2d → 2e
理由：框架是其他功能的地基。

### D-017｜2026-10-23｜✅ 非技術職類改用各自的推薦清單，不再從自動化目錄翻譯
背景：#1 用 `CMAP` 把舊 14 項目錄翻到新框架，業務、創意等職類只看到 MCT、iPAS 這類偏題項目。
決定：biz / ops / pro / creative 各建 12 項 `FW_RECS`（4 證照、4 技能、4 能力）；tech 與 automation 維持 `CAT`。有 key 時可用 AI 依差距補推薦。機會（type o）留給 #6。

### D-018｜2026-10-23｜✅ 計畫項目以「起步清單」為進度單位
決定：每個項目帶 `steps[]`，進度 = 已完成步驟比例；不再用滑桿。加入時依類型套模板、時數依權重分配；使用者可增刪，或用 AI 依背景重新拆解（保留已完成步驟）。全部勾完自動移到「已完成」並寫成長紀錄。
替代方案（未採）：維持滑桿 + 自由文字「下一步」——使用者反映加入計畫後不知道要做什麼。

### D-019｜2026-10-23｜✅ 「本週要做」用簡單規則排程，不做行事曆
規則：進行中 > 待驗收 > 待開始，同類依截止日，再依加入順序；每個項目取下一個未完成步驟，累積到每週可投入時數（可超出至 1.5 倍），最多 3 件。季度回顧以 90 天為週期，從首次使用日起算。

### D-020｜2026-10-23｜✅ 機會每次依差距即時生成，不存檔；擁有者保留精選清單
決定：生成結果只由「框架 + 目前等級 + 目標」決定，不寫進 `S`；id 固定為 `g_型態_能力`，可隨時由 `findItem()` 重建，所以加入計畫、模擬、說帖都不需要另存。AI 改寫只存文字覆蓋（`S.oppText`）。擁有者的 automation 框架保留 16 個手寫「精選機會」與生成結果並列。
理由：差距一變機會就該跟著變；固定 id 讓計畫的 `ref` 與 `inPlan()` 判斷穩定。

### D-021｜2026-10-23｜⏳ Role model 經「特質維度」對應到能力，並疊加在目標角色上
背景：同一個特質（例如「技術深度」）在不同職類對應不同能力，人物無法直接綁定某一套框架。
決定：人物 → 11 個特質維度的加權（+1/+2）→ `TRAIT_MAP[框架]` 對應到具體能力，同一能力取最大值。Role model 是「加味」：目標 = 角色目標 + 加權（上限 5），換角色時保留。每位附「你現在就能做的事」與免責。名單 20 位（含 6 位女性、4 位台灣／華人），Elon Musk 依擁有者要求保留並標註「風格具爭議」。
狀態：擁有者指示先實作再驗收，名單與加權待確認後改為 ✅。

### D-022｜2026-10-23｜✅ 資料以 data/*.json 為唯一來源，建置時注入單一 HTML（解決 D-012 待決事項）
背景：`file://` 不能 fetch JSON；又要維持 D-001 單一 HTML、離線可用。
決定：`data/*.json` 是資料的唯一來源；`python tools/build.py` 驗證後把資料注入 HTML 中 `/*@@DATA-BEGIN … @@DATA-END*/` 區塊（`const DATA={…}`），程式只讀 `DATA`。`--check` 用於 PR / CI。含函式邏輯的 `OPP_TPL`、`EVENTS` 不外部化。使用者端另有「匯入／匯出框架包」，不需重建即可使用社群分享的框架（存在 `S.extFws`）。
替代方案（未採）：獨立 `data/bundle.js`（HTML 變成多檔，分享不便）；執行期 fetch（`file://` 無法使用）。

### D-023｜2026-10-23｜✅ 以 GitHub Pages 公開部署
決定：`deploy-pages.yml` 在 main 更新時先跑 `build.py --check`，再把 App 發佈為 `index.html`。網站不收集任何資料，使用者資料與 API key 仍只存在自己的瀏覽器。之後可綁 RPAI 網域。
替代方案（未採）：先發私人 Claude Artifact 試用。

### D-024｜2026-10-23｜✅ 社群共編：App 內投稿 + Google 表單收件 + 擁有者審核
背景：擁有者希望大家能貢獻職業與對應技能，但只能分享親身經驗、採審核制。
決定：App「🤝 分享經驗」做結構化欄位與檢查（每項能力必附 ≥ 15 字親身例子、親身經驗聲明、授權同意），Google 表單只收 JSON；擁有者在試算表審核，通過後由人／AI 整理進 `data/`（同職業 ≥ 3 份再成框架包）。「不能掰」無法技術上杜絕，靠具體例子、年資職稱合理性與人工審核把關。
替代方案（未採）：GitHub Issue 表單（需 GitHub 帳號，一般人門檻高）；自建共編平台（需後端，列 Phase 3）。

### D-025｜2026-10-23｜✅ 授權 CC BY-NC-SA 4.0，權利人 RPAI 數位優化器、Eddy Wu 吳宗賢
決定：程式與資料統一採 CC BY-NC-SA 4.0；商業使用須取得 RPAI 書面授權。社群投稿者同意以相同條款公開，並另授予 RPAI 數位優化器與 Eddy Wu 吳宗賢非專屬、永久、全球、可再授權（含商業）的使用權，讓投稿內容可用於課程與企業服務。條款文字未經法律審閱，商業化前建議請專業確認。

### D-026｜2026-10-23｜✅ 表單欄位邊打邊存，互動當下再把畫面值寫回
背景：測試回饋基本資料改了沒存、點工作類型會清掉輸入。根因是只在 `change` 寫入，而重畫前某些環境（行動版 Safari、只送 input 的自動化、輸入法組字）不會觸發 `change`。
決定：`input` 事件即時寫入；`flushInputs()` 只在使用者互動當下、只處理目前分頁，把畫面上與 `S` 不同的值寫回。不在 `render()` 裡 flush，否則切到隱藏分頁時會把舊畫面的值蓋回新資料（例如載入範例後）。必填改欄位旁提示。

### D-027｜2026-10-23｜✅ 換能力框架時，由使用者決定舊計畫怎麼處理
決定：未完成且來自舊框架（或能力對應不到）的項目，在 ③ 頂部一次性詢問：重新評估／保留並標示／清空重建；已完成項目一律保留。只換目標角色不詢問，因為能力清單沒變，推薦分數會自動更新。

### D-028｜2026-10-23｜✅ 獨立專家／自由工作者使用客戶語境
決定：階段為 expert 時，說帖改成給潛在客戶的提案（含範圍、報價、成功指標），機會改用接案、開課、客戶提案，並新增「服務產品化與報價」「穩定案源與個人品牌」兩種型態；資料中的組織語境需附 expert 版本，由 `build.py` 檢查。

### D-029｜2026-10-23｜✅ 機會準備度部分計分，經歷算 +0.5 級
決定：準備度 = 各門檻 min(1, 目前 ÷ 需要) 的平均；有對應經歷的能力 +0.5 級；「已準備好」以全部門檻達標判斷。準備度 < 70% 時顯示「下一個能做到的最小任務」。模擬器抽機會卡的門檻由 60 提高到 70，維持原本難度。

### D-030｜2026-10-23｜✅ 外部資料只用授權清楚的來源，並標示框架成熟度
背景：擁有者希望像 1in8b.life 一樣有資料依據。調查後發現原本寫的「參考 SFIA 8 與 O*NET」並未逐項對照，且 SFIA 對外散布需付費授權。
決定：主要依據改為主計總處職業分類、iCAP 職能基準、勞動部薪資開放資料、O*NET（CC BY 4.0）；不使用 SFIA。每個框架標 `maturity`，未逐項對照前一律「草擬版」，App 顯示依據與連結，並註明不代表官方標準。引用格式與限制見 `docs/sources.md`。

### D-031｜2026-10-23｜✅ 遊戲化分數由資料推導，不另外累積
決定：經驗值、等級、成就每次都從目前資料計算（評分、經歷、計畫步驟、回顧、模擬等，部分項目設上限），取消勾選就扣回，避免灌水與資料不一致；只另存 `S.gx`（已看過的成就與等級）決定要不要慶祝。第一次載入或換資料時不慶祝，避免一次跳出一堆。
替代方案（未採）：事件累積制（每次動作加分存檔）——需處理撤銷與重複，容易和實際進度脫鉤。

### D-032｜2026-10-24｜✅ 分享改為一鍵打包，收件改用 Supabase（取代 D-024 的 Google 表單）
背景：擁有者覺得投稿要填的太多，希望直接分享使用者已填的內容；Google 表單不適合收結構化資料，也難以之後做共享資料庫。
決定：分享頁自動打包已填內容，使用者只勾選要分享的區塊與兩個必要聲明，其餘全選填；直接寫入 Supabase `submissions`（anon 只能 INSERT、強制 pending、限頻、email 另存不公開）；送出失敗自動下載檔案。共享資料庫分三階段：先收件審核 → 約 30 筆後顯示匿名相似路徑 → 整體統計。
替代方案（未採）：維持 Google 表單（JSON 貼上體驗差、難查詢）；直接公開所有分享（隱私與真實性風險高）。
